# تنظیمات فراز SMS در WordPress لوکال

## وضعیت تأییدشده

driverپترن Faraz/IPPanel و ذخیرهٔ امن تنظیمات در سطح source/offline test بازبینی شدند. آزمون20/20 مورد جدید،11مجموعهPHPقبلی وlint65فایل گزارش موفق دارد. بازبینی مستقل، مغایرت اعتبارسنجی rawkey پیش ازtrimWordPress را بسته و Important/Critical باقی‌مانده‌ای در محدوده پیدا نکرد.

بررسی خواندنیِ صفحهٔ واقعی مدیریت نیز انجام شد: پنج فیلد زیر موجودند؛ فیلدAPIkey ازنوعpassword، autocompleteoff و valueرندرشدهخالی است. هیچ فرم تنظیمات ارسال، کلید خوانده یا پیامک صادر نشد.

## اصلاح تشخیص سرویس — شاهد جدید اپراتور در ۲۰۲۶-۱۰-۲۲

اپراتور ارسال موفق و دریافت پیامک را از مستند رسمی [ارسال پترن فراز](https://docs.farazsms.com/service/post-ws-v1-sms-pattern) تأیید کرد. این سرویس با فرض قبلی این راهنما متفاوت است:

| قرارداد | سرویس موفق اپراتور | آداپتر فعلی `faraz_ippanel` |
| --- | --- | --- |
| نشانی | `https://api.iranpayamak.com/ws/v1/sms/pattern` | `https://edge.ippanel.com/v1/api/send` |
| هدر کلید | `Api-Key` | `Authorization` |
| بدنه | `code`, `attributes`, `recipient`, `line_number`, `number_format` | `sending_type`, `code`, `params`, `recipients`, `from_number` |

بنابراین پاسخ ۴۰۱ اتصال فعلی، نامعتبر بودن کلید برای API موفق فراز را ثابت نمی‌کند. پیشنهاد قبلی برای تعویض کلید به‌تنهایی کافی نیست؛ اتصال باید به قرارداد صحیح همین سرویس تطبیق یابد. اصلاح Task9D اکنون در سطح source و آزمون آفلاین انجام شده است: درایور مستقل `faraz_iranpayamak` اضافه شده و `faraz_ippanel` با قرارداد و گزینه‌های قبلی Edge بدون مهاجرت کلید حفظ شده است. ارسال واقعی با درایور تازه هنوز توسط این تغییر آزموده نشده است. شماره و کد نمونهٔ اپراتور در این راهنما یا سورس ذخیره نمی‌شوند. توضیحات Edge در ادامه، توصیف آداپتر قبلی‌اند، نه دستور صحیح سرویس موفق جدید.

## Task9D — مسیر جدید Faraz / IranPayamak

این بخش مسیر جدید است؛ بخش‌های Edge و مشاهدات قبلی پایین، سابقهٔ تاریخی‌اند و نباید برای اتصال جدید استفاده شوند. مبنا، مستند رسمی معرفی‌شده توسط اپراتور و حقایق OpenAPI خوانده‌شده در مرحلهٔ تحقیق پیش از منع دانلود با ابزار خط فرمان است؛ در پیاده‌سازی Task9D هیچ صفحه، API یا فایل شبکه‌ای واکشی نشده است.

در صفحهٔ موجود `nahan-settings`، مدیر مجاز باید شخصاً مقادیر زیر را ذخیره کند؛ دستیار این فرم را ارسال نکرده است:

| برچسب / فیلد | گزینهٔ WordPress | مقدار مورد انتظار |
| --- | --- | --- |
| درایور پیامک | `nahan_sms_driver` | `faraz_iranpayamak` |
| Faraz IranPayamak Api-Key | `nahan_sms_iranpayamak_apikey` | کلید این سرویس، فقط خصوصی در فیلد password |
| Faraz IranPayamak Pattern Code | `nahan_sms_iranpayamak_pattern_code` | شناسهٔ پترن تأییدشده، نه OTP |
| Faraz IranPayamak line_number | `nahan_sms_iranpayamak_line_number` | شمارهٔ ملی سرویس دقیقاً مطابق پنل، فقط ارقام ASCII، بدون `+98` و بدون تبدیل E.164 |
| Faraz IranPayamak OTP Variable | `nahan_sms_iranpayamak_variable` | نام دقیق متغیر پترن؛ پیش‌فرضی حدس زده نمی‌شود |

بررسی خواندنیِ صفحهٔ واقعی مدیریت پس از پیاده‌سازی، وجود هر چهار فیلد جدید را تأیید کرد. ورودی کلید از نوع password، با autocomplete خاموش و مقدار HTML خالی بود؛ کلید ذخیره‌شده خوانده نشد. در زمان بررسی، مقدار فعلی فیلد متنی درایور هنوز `faraz_ippanel` بود. هیچ فرم یا ذخیره‌ای توسط دستیار ارسال نشد؛ برای مسیر جدید باید مقدار درایور عمداً به `faraz_iranpayamak` تغییر داده شود. بازبینی مستقل Task9D: تطابق مشخصات و امنیت/کیفیت در محدودهٔ source/آفلاین تأیید شد؛ مورد Important/Critical تأییدشده‌ای پیدا نشد. بازبین ۱۳ تست جدید PHP را نیز مستقلاً و با شبکه غیرفعال اجرا کرد؛ همه موفق بودند. این نتیجه به معنی تأیید ارسال یا تحویل واقعی نیست.

چهار گزینهٔ جدید در نبود مقدار، همگی خالی‌اند. هیچ کلیدی از `sms_faraz_*` خوانده/کپی/مهاجرت نمی‌شود تا برای دامنهٔ جدید ارسال شود. مقادیر Edge در جای خود می‌مانند. فیلد کلید هرگز مقدار ذخیره‌شده را رندر نمی‌کند؛ خالی یا ارسال‌نشده، کلید قبلی همین سرویس را حفظ می‌کند و checkbox جداگانه آن را صریحاً حذف می‌کند. ورودی خام کلید پیش از trim وردپرس اعتبارسنجی می‌شود؛ فاصله و خط جدید به کلید معتبر تبدیل نمی‌شوند. ذخیره با Settings API، nonce و `manage_options` است؛ چهار فیلد جدید با ذخیرهٔ کنترل‌شده و autoload خاموش، حتی در حفظ مقدار بدون تغییر، بررسی می‌شوند.

قرارداد ثابت جدید: `POST https://api.iranpayamak.com/ws/v1/sms/pattern`، هدر خام `Api-Key` (نه `Authorization` و نه `Bearer`)، `Accept` و `Content-Type` برابر `application/json`. بدنه شامل `code`، `recipient` ملی `09…`، `line_number` دقیق ذخیره‌شده، `number_format: english` و شیء `attributes` با نام متغیر تنظیم‌شده و OTP تصادفی فعلی WordPress است. شماره و OTP نمونهٔ اپراتور ذخیره نشده‌اند. timeout ده ثانیه، redirect صفر و پاسخ حداکثر ۱۶ KiB است؛ ارسال مجدد، failover، log fallback و متن آزاد اضافه نشده است.

قرارداد رسمی HTTP **201** را مستند کرده است؛ پس از Task9D، اپراتور دریافت پیامک را گزارش کرد و کنترل‌کننده در بررسی صرفاً خواندنی، رکورد تازهٔ `faraz_iranpayamak` با HTTP **200** و `provider_rejected` دید. بدنهٔ خام آن پاسخ ناشناخته است و از دریافت پیامک، مقدار `status` یا نوع `data` استنتاج نمی‌کنیم. Task9E در سطح source/offline اکنون فقط HTTP **200 یا 201** همراه با `status === success` و `data` از نوع عدد JSON متناهی را می‌پذیرد؛ عدد صفر، منفی یا اعشاری نیز طبق schema عددی معتبر است. bool، رشته، HTTP200/201 تنها، JSON معیوب یا status خطا همچنان پذیرفته نمی‌شود. سایر 2xxها `invalid_response` هستند، نه مدرک رد سرویس؛ non-2xx یا status دقیق `error` همچنان `provider_rejected` است. `messages` به‌علت تناقض schema عمداً نادیده گرفته می‌شود؛ کد vendor مستندی برای این درایور نداریم و نمایش نمی‌دهیم. پذیرش، رسید تحویل نیست. تشخیص Task9C همان رکورد تک‌گزینه‌ای بهترین‌تلاش است، با provider جدید؛ شماره، OTP، کلید، messages، body، headers و data/شناسه در آن ذخیره یا نمایش داده نمی‌شود. ورود کامل با نسخهٔ اصلاح‌شده هنوز در محیط واقعی تأیید نشده و در این کار هیچ درخواست تازه‌ای ارسال نشده است. جزئیات در [گزارش Task9E](../../task-9e-report.md) است.

ذخیرهٔ تنظیمات، policy پیامک واقعی را فعال یا غیرفعال نمی‌کند. ابتدا readiness درایور انتخاب‌شده باید آماده باشد؛ فعال‌سازی مستقل و صریح Task9B و گیت‌های PHP/Next همچنان برقرارند. اگر نصب از قبل armed بوده، ذخیرهٔ provider جدید آن وضعیت را تغییر نمی‌دهد؛ پیش از هر درخواست ورود، وضعیت فعلی را خود اپراتور بررسی کند. هیچ فعال‌سازی یا تغییر env در این کار انجام نشده است. هر آزمون واقعی آینده نیازمند تأیید جداگانه، شمارهٔ تحت کنترل خود اپراتور و فقط یک درخواست در جریان عادی ورود پس از cooldown است؛ پذیرش و دریافت/ورود واقعی باید جداگانه تأیید شوند.

نتیجهٔ این کار صرفاً source/offline است، نه تأیید اعتبار کلید، حساب، موجودی، پترن، شمارهٔ سرویس یا تحویل واقعی. جزئیات آزمون‌ها و خطاهای قدیمی lint در [گزارش Task9D](../../task-9d-report.md) ثبت می‌شود.

## Task9F — مشاهدهٔ امن ساختار پاسخ، بدون تغییر پذیرش

اپراتور دوباره دریافت پیامک و خطای UI را گزارش کرد. کنترل‌کننده در بررسی صرفاً خواندنی، رکورد تازهٔ `2026-10-22T04:58:16Z` با provider=`faraz_iranpayamak`، HTTP200 و outcome=`invalid_response` را دید. این شاهد، ناهماهنگی بدنه با شرط فعلی را نشان می‌دهد، نه اینکه کدام فیلد یا نوع واقعی برگشته است. پاسخ خام گذشته در دسترس نیست و بازسازی نمی‌شود.

Task9F فقط برای تلاش‌های عادی آینده، به همان رکورد تک‌گزینه‌ای مدیریتی، انواع ساختار پاسخ را اضافه می‌کند: `response_root`؛ برای root شیء، `response_status` فقط یکی از `success/error/other/missing/wrong_type` و نوع فیلدهای شناخته‌شدهٔ `data` و `messages`؛ فقط در صورت شیءبودن data، نوع/نبودن خصوصیت شناخته‌شدهٔ `id`؛ و فقط اگر data رشته باشد، پرچم boolean محدود `response_data_numeric_string`. هیچ رشتهٔ status ناشناخته، نام کلید ناشناخته، مقدار شماره/OTP/کلید/شناسه، متن messages، شمارش یا بدنه/هدر خام ثبت نمی‌شود. `invalid_json` و `too_large` فقط enum ثابت‌اند. `true/false` در مدیریت به‌صورت متن ثابت نمایش داده می‌شود؛ مقدار رشتهٔ عددی هرگز نمایش داده یا به عدد پذیرفته‌شده تبدیل نمی‌شود.

شرط پذیرش Task9E **بدون تغییر** است؛ دیدن نوع رشته یا شیء، مجوز پذیرفتن آن نیست. قابلیت فقط `manage_options` است؛ readiness، رندر مدیریت و simulation پیامک یا رکورد مصنوعی ایجاد نمی‌کنند. تلاش اضافی، retry یا endpoint اشکال‌زدایی اضافه نشده است. پس از بازبینی مستقل، تنها خود اپراتور و با تأیید جداگانه می‌تواند یک تلاش عادی آینده پس از cooldown انجام دهد و زمان رکورد را با همان تلاش تطبیق دهد. در این کار هیچ ارسال تازه‌ای انجام نشده و **اصلاح schema واقعی یا ورود کامل تأییدشده ادعا نمی‌شود**. قرارداد دقیق فیلدها و آزمون‌ها در [گزارش Task9F](../../task-9f-report.md) است.

## Task9G — قرارداد عددی شناخته‌شدهٔ `data.id`

شاهد امن تازهٔ کنترل‌کننده از رکورد `2026-10-22T13:38:42Z` برای `faraz_iranpayamak`، HTTP200، root=`object`، status=`success`، data type=`object`، messages type=`missing` و id type=`number` است. مقدار واقعی id خوانده یا ثبت نشده است. همراه با متن رسمیِ ارائه‌شده دربارهٔ `data.id`، این ساختار علت رد توسط شرط قبلیِ صرفاً data عددی را مشخص می‌کند؛ دریافت پیامک نیز توسط اپراتور گزارش شده، اما ورود کامل پس از اصلاح هنوز آزموده نشده است.

Task9G در source/offline فقط این قرارداد دوم را می‌افزاید: HTTP200 یا201 و status دقیق `success`، با data عدد JSON متناهی **یا** data شیء JSON ساده با خصوصیت شناخته‌شدهٔ `id` از نوع عدد JSON متناهی. صفر، عدد منفی و اعشاری محدودیت حدسی مثبت/صحیح ندارند؛ شاهد واقعی فقط نوع را نشان داده، نه مقدار. رشته/boolean/null/list/شیء یا عدد نامتناهی برای id و همچنین id غایب رد می‌شوند. تبدیل رشته به عدد، پذیرش بر اساس diagnostic، schema تو‌در‌توی ناشناخته یا پذیرش همهٔ 2xx اضافه نشده است. هیچ ID یا مقدار خامی به خروجی، لاگ یا ذخیرهٔ diagnostic اضافه نشده؛ فقط typeهای امن Task9F باقی‌اند.

این اصلاح فقط شرط قرارداد پاسخ را تغییر می‌دهد؛ درخواست، تنظیمات، Edge، Origin، گیت فعال‌سازی، invalidation، throttle، CAS و بهترین‌تلاش diagnostic دست‌نخورده‌اند. هیچ پیامک/HTTP یا ذخیرهٔ مدیریت توسط دستیار انجام نشده و env خصوصی/سرور موجود تغییر نکرده است. جزئیات آزمون و دامنه در [گزارش Task9G](../../task-9g-report.md) است. توضیح Task9F دربارهٔ نامعلوم‌بودن schema، وضعیت تاریخی قبل از شاهد جدید است؛ نیاز به بررسی مستقل و آزمون زندهٔ جداگانه همچنان باقی است.

## محل ورود اطلاعات آداپتر قبلی (فقط Edge، نه مسیر جدید)

لوکال: `http://localhost/karban/wp-admin/admin.php?page=nahan-settings`

- **درایور پیامک:** `faraz_ippanel`، دقیق و بدون فاصله.
- **Faraz / IPPanel API Key:** کلید دسترسی پنل خودتان؛ در گفتگو یا فایل پروژه قرار ندهید. درروشاینadapterنامکاربری/رمزلازم نیست.
- **Faraz Pattern Code:** شناسهٔ پترن تأییدشدهٔ ارسالOTP، نه خودکدیکبارمصرف.
- **Faraz Originator (E.164):** شمارهٔ فرستندهٔ مجازِ واقعی پنل در قالبE.164؛ مقدار را ازپنل بگیرید، حدس نزنید.
- **Faraz OTP Variable:** نام دقیق متغیر پترن؛ `code` فقط وقتی درست است که متغیر پترن شما همین نام را دارد.

کلید ذخیره‌شده درHTML بازگردانده نمی‌شود؛ ورودی خالی/ارسال‌نشده، مقدار قبلی را نگه می‌دارد. حذف با intentصریحِ کنترلپاک‌کردن است. فاصله/خط‌جدید درکلید به‌عنواناشتباه رد می‌شود، نه اصلاحخودکار. گزینه‌های SMS با sanitize/capability/nonce وautoloadغیرفعال ذخیره می‌شوند؛ ادعای encryptionجدید برایoptionsنشده است.

## وضعیت آزمون واقعی — به‌روزرسانی ۲۰۲۶-۱۰-۲۲

اپراتور تنظیمات را ذخیره و حالت پیامک واقعی محلی را فعال کرده است. بررسی خواندنیِ readiness، حالت `sms`، طول کد ۵ و آماده‌بودن هر دو schema، پیکربندی provider و مجوز پیامک واقعی محلی را تأیید کرد. opt-in مستقل Next نیز پس از این بررسی فعال شد. بنابراین توضیح قبلی دربارهٔ فعال‌بودن فعلی کد ثابت، دیگر وضعیت این نصب نیست؛ `145632` در حالت SMS معتبر نیست.

اپراتور هنگام درخواست واقعی خطای عمومی ورود و سپس محدودیت درخواست را گزارش کرد و دریافت‌نشدن پیامک را تأیید کرد. علت دقیق خطای قبلی هنوز **نامشخص** است؛ پاسخ تاریخی provider در دسترس نیست. آمادگی پیکربندی، اعتبار کلید یا موجودی حساب و پذیرش یا تحویل پیامک را ثابت نمی‌کند. دستیار پیامک واقعی ارسال نکرده است.

اصلاح Task9C برای تفکیک امن خطاهای پیکربندی، ارتباط و پاسخ provider پیاده‌سازی و در محدودهٔ source/آفلاین مستقل تأیید شد؛ مورد Important/Critical تأییدشده‌ای یافت نشد. بازبین مستقلاً ۱۱ تست PHP و ۳ تست Node مربوط به این تغییر را نیز اجرا کرد. نتیجهٔ آخرین تلاش بعدی در بخش مدیریتی «آخرین تلاش ارسال پیامک ورود» نمایش داده می‌شود؛ این قابلیت گذشته را بازسازی نمی‌کند. آزمون‌های آفلاین نهایی: ۱۴ مجموعهٔ PHP و ۳۰۳ تست Node، TypeScript، lint محدود و build مستقل موفق؛ lint کل مخزن همچنان ۴ خطای قبلی دارد. جزئیات در [گزارش Task9C](../../task-9c-report.md).

- outcome: `provider_rejected`
- HTTP: `401`

این بررسی فقط GET/خواندن صفحه بود؛ دستیار هیچ ارسال یا ذخیرهٔ تنظیماتی انجام نداد و کلید خوانده نشد. زمان رکورد هنوز به یک تلاش مشخص اپراتور تطبیق داده نشده؛ بنابراین علت همهٔ تلاش‌های تاریخی یا نتیجهٔ تحویل از آن استنتاج نمی‌شود. پاسخ ۴۰۱ مسیر بررسی احراز هویت/دسترسی API را اولویت می‌دهد، نه تغییر حدسی پترن یا متغیر. مستند رسمی، هدر `Authorization: YOUR_TOKEN_HERE` بدون پیشوند `Bearer` و ساخت کلید از بخش Developers → Access Keys پنل را نشان می‌دهد؛ دلیل خاص ۴۰۱ این حساب در آن مشخص نشده است.

### گردش کار قبلی فعال‌سازی Edge — تاریخی، نه دستور Task9D

برای اتصال Faraz جدید، فقط فیلدها و درایور بخش Task9D بالاتر ملاک‌اند. مراحل زیر سابقهٔ گردش کار قبلی با `faraz_ippanel` هستند؛ انتخاب آن برای سرویس IranPayamak درست نیست.

1. مقادیر Faraz را در همین صفحهٔ مدیریت ذخیره کنید؛ driverباید `faraz_ippanel` باشد و Pattern/Originator/Variable واقعیپنل را ازخودپنل بگیرید. کلید را درگفتگو نفرستید.
2. دربخش مستقل «پیامک واقعی محلی»، پس ازخواندن هشدار هزینه وکول‌داون، عبارت `ENABLE_REAL_SMS` را خودتان وارد و «فعال‌سازی پیامک واقعی محلی» را بزنید. این اقدامcapability+POST+nonce جدا، gateمحلی وprovider/schema readiness را کنترل می‌کند و پیامک نمی‌فرستد.
3. فعال‌سازی، challenge/نشست‌های صادرشده باکدثابت را نامعتبر می‌کند؛ آن‌ها بهSMSواقعی تبدیل نمی‌شوند. sessionمدیرعادیWordPress بااینJWTمحلی یکی نیست.
4. readiness واقعی باید mode=`sms`،codeLength=5،otpSchemaReady=true،credentialSchemaReady=true،providerConfigured=true وlocalRealSmsAllowed=true باشد. این‌ها فقط آمادگیپیکربندی‌اند، نه تضمیناعتبارکلید/موجودی/تحویل.
5. مستقل ازPHP، Next به `KARBAN_ALLOW_LOCAL_SMS=true` درenvخصوصی نیاز دارد؛ base `KARBAN_LOCAL_DEVELOPMENT=true`،origin/محیطlocal نیزلازم‌اند. تاoperatorعمداًmodeرافعالونتیجه‌اش تأییدنشده، این flagاضافهیاtrueنشود؛ مقدارغایب/false قبل ازOTPحالتSMSرا503می‌کند و پیامکی صادرنمی‌شود.
6. بعد ازتطابقهردوreadiness، فقط یکبارفرم ورود با شمارهٔ تحتکنترل خودتان وکدتصادفی واقعی دریافتی آزموده شود. کدثابت145632 دراینحالت نیست؛ OTPواقعیپنج‌رقمی است. هیچ گیرنده‌ای ازحساب‌ها استخراج/حدس زده نمی‌شود.

خاموش‌کردن ازعملیات مستقل «خاموش کردن پیامک واقعی محلی» و سپس حذف/falseکردن opt-inNext انجاممی‌شود؛ بازگشتکدثابت فقطاگرگیت‌هایقبلی سالمباشند. خطا/timeout خودکار تکرار یا دورزدنکول‌داون ندارد. کدموضوعی را صرفاً برای دورزدنreadiness تغییرندهید.

پس ازتکمیل وبازبینیpolicy، یکآزمون واقعی کنترل‌شده فقط با شمارهٔ تحتکنترل اپراتور و انتخابصریح ارسال انجام می‌شود. APIacceptance تحویلپیامکنیست؛ رسیدنپیامکوورودباهمانکدتصادفی جداگانه تأیید می‌شود. خطا/timeoutخودکارتکرارSMSیاfallbackبهlog/کدثابتندارد.

ارسالپترن ازHTTPSثابت `https://edge.ippanel.com/v1/api/send` وکلیدسرورانجاممی‌شود؛ وب‌سرویسloginپنلبرایOTPکاربراناشتباهگرفتنمجازنیست. سازگاریهمینکلید/حساب/پترن باآداپتربایددرآزمونواقعی بعدی ثابتشود، نه ازوجودفیلدهایپنل.
